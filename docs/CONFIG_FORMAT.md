# CONFIG_FORMAT — FF14 設定ファイルの形式（調査結果）

- 文書ステータス: 調査中 v0.1（2026-09-24）
- 調査に使ったファイル: `main` の `samples/hotbar-hud/HOTBAR.DAT`（204,832 バイト）、`UISAVE.DAT`（296,992 バイト）
- 関連: [INPUT_HUD.md](./INPUT_HUD.md)（CFG-01〜07）

> ここに書いた形式は、**サンプル 1 組から読み取ったもの**。別のキャラクター・別のパッチでも同じかは、まだ確かめていない。
> 実装では、想定と違うデータを見つけたら、推測で読み進めずに「読めなかった」として止める。

## 1. 共通のファイル構造（HOTBAR.DAT / UISAVE.DAT で一致）

| 位置 | 大きさ | 中身 | サンプルの値 |
|------|--------|------|-------------|
| 0x00 | u16 | ファイルの種類・版と思われる値 | HOTBAR: 2 / UISAVE: 9 |
| 0x02 | u16 | 不明 | HOTBAR: 4 / UISAVE: 1 |
| 0x04 | u32 | ファイル長 − 32 | 204,800 / 296,960 |
| 0x08 | u32 | 有効データの長さ `n` | 152,064 / 133,562 |
| 0x0C | u32 | 0 | 0 |
| 0x10 | n バイト | **有効データ。全バイトを `0x31` と XOR して難読化されている** | |
| 0x10+n 〜 末尾 | | 0 埋め（XOR されていない） | |

- XOR の鍵 `0x31` は、有効データの中で `0x31` が際立って多い（元が 0 のバイト）ことから求め、HOTBAR の全レコードの規則性で確かめた。
- 以下の「オフセット」は、XOR を戻した有効データの先頭からの位置。

## 2. HOTBAR.DAT（CFG-01: 解読済み）

### 2.1 レコード

有効データ = **8 バイトのレコードの並び**（152,064 / 8 = 19,008 件）。

| 位置 | 型 | 中身 |
|------|----|------|
| +0 | u32 | 中身の ID（種類が 1 のときはアクション ID） |
| +4 | u8 | セット番号（§2.2） |
| +5 | u8 | バー番号: 0〜9 = ホットバー 1〜10、10〜17 = クロスホットバー 1〜8 |
| +6 | u8 | スロット番号 0〜15 |
| +7 | u8 | 種類（§2.3）。0 = 空き |

- 1 セット = 18 バー × 16 スロット = 288 レコード（2,304 バイト）。66 セット。
- ブロックの順番とバー・スロットの番号は、全件で規則どおりに並んでいた（食い違い 0 件）。
- 通常のホットバーでも 16 スロット分の枠があるが、ゲームで使うのは 12 スロット（13〜16 番目は常に空きだった）。

### 2.2 セット番号

| ブロック（先頭から何番目か） | セット番号 | 中身 |
|---------------------------|-----------|------|
| 0 | 0 | **共有のバー**（「全ジョブで共有する」設定にしたバーの中身）。侍のセットに中身がないホットバー 5〜10・クロスホットバー 7〜8 が、セット 0 に入っていた（エモート・マウントなどのほか、他のジョブのアクションも残っている）。どのバーが共有かの設定は HOTBAR.DAT にない（CFG-08） |
| 1〜43 | 1〜43 | **ClassJob の ID と一致**（例: 19 = ナイト、34 = 侍、43 = 最新の追加ジョブ）。8〜18 はクラフター・ギャザラー |
| 44〜65 | 64〜85 | 不明（22 セット。PvP 用の可能性。TODO(CFG-09)）。サンプルでは 1 セットにだけ中身があった |

根拠: 各セットの種類 1 の ID を `jobs.json` の `actionIds` と照らし、最も一致するジョブがセット番号の ClassJob と一致した（例: セット 34 → 侍 63/66 件）。

### 2.3 種類（+7）

| 値 | 意味 | 根拠 / 状態 |
|----|------|-------------|
| 0 | 空き | |
| 1 | アクション | 戦闘ジョブのセットでは、ほぼすべて `actions.json` に存在する。クラフター用のアクションは `actions.json`（PvE 戦闘のみ）にないため、一致しない |
| 2 | アイテムと思われる | ID が Item シートの範囲。未確認 |
| 10, 17 など | アクション以外（一般アクションなど） | 名前の対応は未確認（TODO(CFG-10)）。練習では「使えないマス」として扱う |
| その他（4, 6, 7, 8, 9, 11, 12, 15, 16, 18, 24〜31） | 不明 | 練習では使わない |

### 2.4 侍（セット 34）のサンプルで分かったこと

- ホットバー 1〜4 と、クロスホットバー 1〜3 に中身があった。
- **ホットバーには下位版のアクションが入っている**（刃風 7477。Lv100 では暁風になる。心眼 7498 → 天眼通）。読み込み時に `upgradesFrom` で上位版に解決する設計（INPUT_HUD §5.3）は必須。
- 居合術（7867）・燕返し（16483）は置き換え前のボタンとして入っている。置き換え先（彼岸花など）は入っていない。これは設計（ButtonDef の置き換え）と一致する。
- **今は存在しないアクション**（7494, 7501, 7502）が残っていた。`actions.json` にない ID は「使えないマス」として表示する。

### 2.5 まだ分からないこと

| ID | 内容 |
|----|------|
| CFG-08 | どのバーを共有にしているかの設定の保存場所（HOTBAR.DAT にはない。UISAVE.DAT などを §4 の方法で調べる）。それまでは「ジョブ専用のバーに中身があればジョブ専用、なければ共有」と推定し、画面で切り替えられるようにする |
| CFG-11 | 「アクションを変化させない（別ボタンにする）」設定の保存場所と、その設定のときの元ボタンの動き。それまでは「変化先がホットバーに直接置かれていれば、変化させない設定」と推定する（変化先は通常ホットバーに登録できないとツールチップにあるため）。今回のサンプルでは該当なし |
| CFG-09 | セット 64〜85 の意味 |
| CFG-10 | 種類 2 以外のアクション以外の種類の意味 |
| CFG-02 | キー割り当て（KEYBIND.DAT）。サンプルなし |

## 3. UISAVE.DAT（途中）

- 共通構造（§1）は同じで、XOR `0x31` を戻すと、先頭 16 バイトの後にセクションが続く。
- セクションの見出しは `u16 番号, u16 種類, u32 長さ, …`（16 バイト）で、本体の後に 4 バイトが続く。先頭の 3 セクションはこの規則で読めたが、4 つ目で規則から外れた。
- 一部のセクションは、さらに **`0x73` で XOR** されている（XOR 後のデータで `0x73` が際立って多い）。
- **HUD の配置が入っているかどうかは、まだ分かっていない。** 一般には HUD の配置は `ADDON.DAT` にあると考えられるが、未確認（CFG-03）。

### 3.1 個人情報についての注意（重要）

- UISAVE.DAT には、XOR を戻すと **他のプレイヤーのキャラクター名が数十件**、平文で入っている（交流履歴・フレンド・ブラックリストなどの一覧と思われる）。
- ファイル先頭のセクションの近くに、**キャラクターの内部 ID と思われる 64 ビットの値**がある。
- XOR で隠されているため、そのままの状態で文字列を検索しても見つからない。
- このため、INPUT_HUD §5.1 の「読むファイル」から **UISAVE.DAT を外す**。HUD の配置は ADDON.DAT の調査を待つ。
- アプリで読み込むときも、読んだ内容のうち**必要な項目（アクション ID・座標）以外は保存も表示もしない**（INPUT_HUD §5.2 のとおり）。

## 4. 設定の保存場所の調べ方（中身を公開せずに）

共有バーの設定（CFG-08）やアクションの変化の設定（CFG-11）のように、**設定を 1 つ変えると変わる場所**は、変更前後のファイルを比べれば分かる。
比べる道具 `tools/cfg-diff/diff.mjs` は、変わったバイトの**位置と値だけ**を出し、文字列（キャラクター名など）は出さない。出力はそのまま共有してよい。

1. ゲームを終了した状態で、`FFXIV_CHR…` フォルダの対象ファイル（例 `UISAVE.DAT`）を別の場所にコピーする（変更前）。
2. ゲームで設定を**1 つだけ**変える（例: ホットバー 5 の「共有」をオンにする / 居合術の「アクションの変化」を切り替える）。ゲームを終了する。
3. 同じファイルをもう一度コピーする（変更後）。
4. `node tools/cfg-diff/diff.mjs 変更前/UISAVE.DAT 変更後/UISAVE.DAT` を実行し、出力を共有する。

> サンプルファイルそのものは公開リポジトリに入れない。特に UISAVE.DAT は §3.1 のとおり他のプレイヤーの名前を含む。

## 5. 公開前の確認（個人情報）

サンプルを公開リポジトリに入れる前に、`node tools/cfg-diff/check-strings.mjs <ファイル>` を**自分の PC で**実行し、隠された中身に読める文字列（名前など）がないかを確かめる。
確認結果: HOTBAR.DAT は 0 種類（問題なし）。UISAVE.DAT は 129 種類（他のプレイヤー名を含むため公開不可）。

## 6. KEYBIND.DAT（解読済み）

- 共通ヘッダー（§1）の後の有効データを **`0x73` で XOR** すると、`T 長さ 名前\0 C 長さ 値\0` の並びになる（名前は `HOTBAR_1_1` などのコマンド名）。
- 値は `キー.修飾,キー.修飾,`（16 進）。1 つ目が主、2 つ目が副の割り当て。`00.00` は未割り当て。
- キーは **Windows の仮想キーコード**（例 `31` = 1、`46` = F、`70` = F1、`61` = テンキー 1、`6A` = テンキー *）。
- 修飾はビットの組み合わせ（`01` `02` `04`）。**1 = Shift、2 = Ctrl、4 = Alt と推定**（サンプルではホットバー 3 が `01` と `02` の 2 組、ホットバー 2 が `04`）。ゲーム内の表示と照らして確認する（CFG-12）。
- ホットバーは `HOTBAR_<バー 1〜10>_<スロット 1〜9,0,A,B>`。サンプルではホットバー 1〜4・6〜9 に割り当てがあった。
- 文字列の検査（§5）: コマンド名のみで、人の名前などは含まれない。

## 7. ADDON.DAT（ホットバー部分は解読済み）

- 共通ヘッダー（§1）の後は **XOR なし**。先頭が `ADDN`、+0x20 に配置の名前（`Default`）、+0x50 にレコード数（サンプル 479）。
- +0x60 から **32 バイトのレコード**が並ぶ。

| 位置 | 型 | 中身 |
|------|----|------|
| +0 | u32 | 部品の名前のハッシュ（計算方法は未特定。CRC32・FNV などでは一致しなかった） |
| +4 | f32 | X 座標（画面の幅に対する %） |
| +8 | f32 | Y 座標（画面の高さに対する %） |
| +12 | f32 | 倍率（HUD レイアウトの「サイズ」。例 0.8・0.6） |
| +16 | u32 | 識別値。ホットバーは **下位バイト = ホットバー番号 0〜9、次のバイト = 並び**（1 = 12×1、2 = 6×2、3 = 4×3、4 = 3×4、5 = 2×6、6 = 1×12） |
| +20 | u16 ×2 | 幅・高さ（倍率 1 のときの大きさ。12×1 のホットバーは 624×72） |
| +24 | u8 | 基準点（テンキー配置と同じ並び: 0 左上 1 上 2 右上 3 左 4 中央 5 右 6 左下 7 下 8 右下） |
| +27 | u8 | 表示（`FF` = 表示、`EE` = 非表示と推定。サンプルでは非表示のホットバー 5 だけが `EE`） |

- レコード 0〜446 はメニュー類のウィンドウ位置、447 以降が HUD の部品と思われる。
- ホットバー以外（キャストバー・ターゲット情報・バフ表示など）は、位置と大きさは読めるが、**どのレコードが何かはまだ特定できていない**（CFG-13）。HUD レイアウト画面のスクリーンショットと位置を照らし合わせれば特定できる見込み。
- **ジョブゲージは大きさで特定できる**: レコードの幅×高さが、ゲージの ULD（`src/data/ffxiv/job-gauges.json`）の一番外側のノードの大きさと一致する。侍はサンプルに 1 つずつだけあった（ハッシュもゲージごとに固定と思われる）。

| ゲージ | ULD の大きさ | サンプルのレコード | 位置・倍率・基準点 |
|--------|-------------|------------------|-------------------|
| 剣気・剣圧（`JobHudSAM0`） | 330×88 | #356（ハッシュ `ecb607d5`） | X 37.55%・Y 46.85%・0.8・中央 |
| 閃（`JobHudSAM1`） | 170×158 | #355（ハッシュ `ed746de2`） | X 34.64%・Y 55.74%・0.8・中央 |

- このレコードの +27（表示）は `00` だった（ホットバーの `FF` / `EE` とは別の意味と思われる）。モックは `CfgParse.findGauges()` で大きさが一致するレコードが 1 つだけのときに使う。
- 大きさの基準（1080 の画面で倍率 1 のときの px とみなしている）は推定。ゲーム内の「HUD の大きさ」設定との関係も未確認（CFG-14）。

## 8. FFXIV.cfg（テキスト）

- `キー<TAB>値` の行が `<Display Settings>` などの見出しごとに並ぶ。XOR なし。
- **公開しない項目がある**: `LastLogin0/1`、`WorldId`、`ScreenShotDir`（Windows のユーザー名を含むパス）など。サンプルには画面と HUD の大きさ、パッドのボタン設定だけを抜き出して入れた（`samples/hotbar-hud/FFXIV.cfg`）。

| キー | サンプルの値 | 意味 |
|------|-------------|------|
| `ScreenMode` | 2 | 画面モード。0 ウィンドウ / 1 フルスクリーン / 2 仮想フルスクリーンと推定 |
| `ScreenWidth` / `ScreenHeight` | 3840 / 2129 | ウィンドウの大きさ（タスクバーを除いた大きさと思われる） |
| `FullScreenWidth` / `FullScreenHeight` | 3840 / 2160 | フルスクリーン時の解像度。モード 1・2 ではこちらを使う |
| `UiHighScale` | 2 | HUD の大きさ（高解像度 UI）。0=100%・1=150%・2=200%・3=300% と推定（CFG-14） |
| `UiBaseScale` | 3 | 不明 |
| `PadButton_L2` / `R2` / `R1` | XHB_Left_Start / XHB_Right_Start / Hotbar_Set_Change | パッドのボタンの役割。クロスホットバーは L2/R2、セット切り替えは R1 |

- 4K・HUD 200% のときの ADDON.DAT の大きさ（倍率 1 で 12×1 のホットバーが 624×72）は、「ゲーム画面の px = 大きさ × 倍率 × HUD の大きさ設定」とみなすと、1080p・100% と同じ見た目になり、辻つまが合う。
