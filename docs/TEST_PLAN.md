# TEST_PLAN — テスト計画

- 文書ステータス: Draft v0.1
- 前提: [SPEC.md](./SPEC.md), [STATE_MACHINE.md](./STATE_MACHINE.md), [DATA_SCHEMA.md](./DATA_SCHEMA.md)

## 1. 方針

| 方針 | 内容 |
|------|------|
| エンジンを厚くテスト | 判定ロジックは `src/engine/`（純粋 TS）に集約し、Vitest の単体テストで網羅する。UI テストは薄く |
| ゲームデータに依存しないテスト | エンジン・採点のテストは **架空のテストジョブ**（`_testjob`、値はテスト用の切りのよい数値）で行う。侍の値が未確認でもテストを書ける |
| 時刻は仮想時計で | `performance.now()` / タイマーをテストで使わない。`advanceTo(t)` と `input(id, t)` の列で状態を作る |
| シナリオは入力ログで記述 | テストケースを `[{ t, buttonId }]` と「期待イベント」の組で書き、読みやすくする（テーブル駆動） |
| データは検証テストで守る | JSON スキーマ・参照整合性・`null` の有無をテストで検査する |
| CI | PR ごとに `typecheck` / `lint` / `vitest run` / `vite build` を GitHub Actions で実行 |

### 1.1 テストジョブ（`_testjob`）の構成例

以下は **ゲーム仕様ではなく、テスト用に作る架空データ** の例。

| 種類 | 内容 |
|------|------|
| system | GCD 2500ms、ロック 600ms、キュー 500ms、コンボ受付 30000ms（すべて架空値） |
| GCD | `t1`（始動）→ `t2`（`t1` からコンボ）→ `t3`（`t2` からコンボ、ゲージ +10）、`tCast`（詠唱 1000ms）、`tNoBreak`（`breaksCombo: false`） |
| oGCD | `o1`（リキャスト 60000ms）、`o2`（2 チャージ、30000ms）、`oSpend`（ゲージ 50 消費）、`oReset`（`o1` のリキャストリセット） |
| ステータス | `buffA`（自己、20000ms、replace）、`dotB`（敵、30000ms、replace）、`hasteC`（GCD ×0.9）、`stackD`（最大 3 スタック） |
| リソース | `gauge`（0〜100）、`flagX` / `flagY`（フラグ） |
| ボタン | `bT1` の slots: `stackD` 中は `tAlt`、それ以外は `t1`（置き換えのテスト用） |

## 3. エンジン単体テスト（U-）

### 3.1 時間と GCD

| ID | ケース | 期待 |
|----|--------|------|
| U-GCD-01 | t=0 で GCD 使用 | `gcd.readyAt = 2500`, `lock.until = 600` |
| U-GCD-02 | t=1000 に次の GCD を入力（受付時間外） | 拒否 `ON_COOLDOWN`、残り 1500ms を detail に含む |
| U-GCD-03 | t=2100 に次の GCD を入力（受付時間内） | キューされ、t=2500 ちょうどに実行（`ACTION_EXECUTED.t = 2500`） |
| U-GCD-04 | キューの後勝ち | t=2100 に A、t=2200 に B → t=2500 に B が実行、A は `QUEUE_DROPPED` |
| U-GCD-05 | `hasteC` 中の GCD | リキャスト 2250ms（テストデータの倍率どおり） |
| U-GCD-06 | 詠唱あり GCD | 詠唱中は他入力がキューまたは拒否、効果は詠唱完了時刻に適用 |
| U-GCD-07 | tick の粒度に依存しない | 同じ入力ログを tick 間隔 1ms / 16ms / 100ms で進めてもイベント列が一致 |

### 3.7 プロパティテスト（任意・余力があれば）

- ランダムな入力ログ（`fast-check`）に対し、以下の不変条件が常に成り立つ:
  - リソースは `0..max` の範囲
  - チャージは `0..maxCharges`
  - `GCD_IDLE` + `CLIPPED` + GCD 稼働時間 = 評価対象時間
  - イベントの時刻は単調非減少

## 10. ゲームデータの確認手順（侍データ入力 PR 用）

エンジンのテストとは別に、侍データが実ゲームと一致しているかを人が確認する。

1. 各 TODO(GAME-xx) について出典（公式ジョブガイド・パッチノート）を `DataSource` に登録する。
2. 値を入力し、該当エントリを `verified` にする。出典が見つからない値は `null` のまま残す。
3. 可能なら実ゲームの木人で開幕回しを実行し、アプリの「お手本時刻」と大きな差がないかを確認（確認者・日付を PR に記載）。
4. D- テストがすべて通ることを確認する。
